# Причинный бэктест фьючерсов

Реализация: `statarb.research`; расчёты исполнения, позиций и переоценки общие с paper/replay. Правила описаны в [контракте](../contracts/causal-futures-research.md) и [ADR 0005](../../adr/0005-causal-futures-research-and-shared-paper-ledger.md).

## Подготовка входов

Нужны два CSV с `time,open,high,low,close,volume` либо Parquet с `bar_start_utc` и теми же OHLCV. `time` — начало бара в Unix seconds UTC. Укажите фактическую длительность бара в секундах. Пропуски и разные сетки допускаются, но исполнение возможно только на общих барах. Пересекающиеся бары, противоречащие дубликаты, NaN/inf и неверные OHLC отклоняются.

Подготовьте JSON спецификаций `{"instruments": [...]}`. Каждый элемент содержит:

| Поле | Содержание |
| --- | --- |
| `instrument` | `{"symbol": "SRM5", "exchange": "MOEX", "instrument_type": "future"}` |
| `version`, `source` | Версия и проверяемый источник исторических параметров |
| `valid_from`, `valid_until` | UTC ISO-8601; конец интервала исключается, может быть null |
| `tick_size`, `tick_value` | Шаг котировки и рублёвая стоимость шага одного контракта |
| `contract_size` | Размер базового актива в контракте; не умножать на него стоимость шага повторно |
| `initial_margin_long`, `initial_margin_short` | Историческое ГО на контракт для каждого направления |
| `last_trade_at` | Последнее время обращения в UTC ISO-8601 |
| `currency` | `RUB` |

Денежные значения передавайте строками. Все версии должны покрывать исследуемую историю; перекрытия и изменение стоимости пункта внутри прогона отклоняются. `catalog_from_alor_snapshots` сохраняет параметры с момента наблюдения; он не превращает сегодняшний snapshot в историческую спецификацию. В имеющихся CSV этих параметров нет: их нужно предоставить отдельно. Значения из `synthetic_smoke_catalog` предназначены только для тестов контрактов.

## Конфигурация и запуск

Пример структуры конфигурации; денежные допущения здесь демонстрационные, замените их своими:

```json
{
  "left": {"instrument": {"symbol": "SRM5", "exchange": "MOEX", "instrument_type": "future"}, "bars": "SRM5.csv"},
  "right": {"instrument": {"symbol": "SPM5", "exchange": "MOEX", "instrument_type": "future"}, "bars": "SPM5.csv"},
  "specifications": "historical-specifications.json",
  "timeframe_seconds": 3600,
  "initial_cash": "1000000",
  "pair_budget": "100000",
  "max_hedge_error": "0.05",
  "costs": {"broker_per_contract": "1", "exchange_per_contract": "1", "spread_bps": "5", "slippage_bps": "2", "broker_vat_rate": "0"},
  "risk_policy": {"max_order_quantity": "100", "max_abs_position": "100"},
  "strategy": {"lookback": 60, "min_estimation_window": 512, "recompute_frequency": 16, "entry_threshold": 2.0, "exit_threshold": 0.5, "min_avg_volume": 200},
  "session_id": "sber-research-001"
}
```

Пути входов разрешаются относительно файла конфигурации. Пути отчёта и журнала должны отличаться друг от друга и от всех входных файлов, включая конфигурацию, бары, спецификации и календарь; совпадение отклоняется до исполнения. Необязательные `from_time`/`to_time` — UTC ISO-8601; берутся только полностью завершённые бары внутри `[from,to)`, а прогрев проходит внутри выбранного отрезка. `trading_start` отдельно ограничивает начало оценочного периода, сохраняя предшествующую историю для обучения. `trading_calendar` может указывать на JSON вида `{"2025-06-02T20:00:00+00:00": "2025-06-02", ...}` с биржевым торговым днём каждого оценочного бара. При отсутствии карты результат явно использует наблюдаемые московские даты с исключённой границей конца бара.

```bash
uv run python -m statarb.research.cli --config research.json --output results/run-001.json --journal results/run-001.jsonl
```

Старый `python -m core.backtest` принимает тот же CLI. В Python используйте `BacktestRequest`, `run_backtest` или `Backtester(request=request)`. Для разных тарифов ног `BacktestRequest.costs` принимает отображение `InstrumentRef -> ExecutionCosts`.

Выход содержит equity, модель и решения на каждом шаге, финансовые события, издержки, остатки позиций и стоимость предполагаемой ликвидации. Все исходные допущения, версии спецификаций и хеши баров сохраняются. `no_trades` — допустимый результат, а недостаточная история/спецификации — диагностическая ошибка. Каждый прогон использует новый путь журнала. Результаты `run_universe` относятся к независимым счетам пар и не складываются в портфель.

Для дополнительного bootstrap добавьте `"bootstrap": {"horizon_days": 20, "block_days": 5, "seed": 7, "simulations": 1000}`. Дневной VaR/ES без достаточной истории и Sharpe при нулевой дисперсии отображаются как недоступные значения.

## Replay и восстановление

Для CSV-снимка незавершённой сессии указывайте `available_at`: UTC время, до которого котировки действительно наблюдались. Бар с концом после этой границы не используется, даже если `to_time` позже. По умолчанию граница — момент создания запроса; это предполагает, что старые CSV содержат окончательные закрытия. В Alor manifest bridge граница берётся из времени загрузки с учётом заявленной задержки. Для журнала используются POSIX file locking и fsync, как в текущих Linux deployment profiles.

```python
from statarb.domain import InstrumentCatalog
from statarb.runtime.replay import RuntimeReplayer, load_event_journal

catalog = InstrumentCatalog.load("historical-specifications.json")
replay = RuntimeReplayer(account_id="backtest-pair", starting_cash="1000000", instrument_catalog=catalog)
result = replay.replay(load_event_journal("results/run-001.jsonl"))
```

Используйте те же капитал, идентификатор счёта и версии спецификаций. Каждый промежуточный снимок проверяется независимо; подмена PnL, цены, денег или ГО приводит к ошибке.

Для продолжения paper-сессии используйте `PaperExecutionEngine.recover(journal_path=..., account_id=..., starting_cash=..., risk_policy=..., instrument_catalog=...)`. Если остался неполный хвост записи, передайте `new_journal_path` для восстановления только подтверждённых событий в новый файл. Исходный журнал сохранится. После ошибки записи прежний engine не принимает новые операции.

Снимок `paper_trading_day` остаётся отдельным smoke контрактов с явно синтетическими параметрами. На текущих данных последняя рекомендация flat: корректный smoke содержит две отметки цены, два снимка и один итог счёта, без фиктивного открытия старого сигнала. Полное исполнение стратегии проверяется финансовыми тестами.

Форматирование всех 67 изменённых/новых Python-файлов проверено отдельно. Оба CLI (`core.backtest` и `statarb.research.cli`) и все 36 совместимых экспортов `core` доступны. Финансовые регрессии включают полный цикл с реальной оценкой коинтеграции на синтетической истории, исполнением и независимым replay; это проверка реализации, а не оценка доходности на рыночных данных.

При проверке согласованности исправлены три дополнительных случая: время обучения пары после разрыва общей сетки, сохранение reference identity/lot size через публичные HTTP/WS mapper-входы и запрет перезаписи любого входного файла отчётом либо журналом. Регрессионные проверки включены в полный набор.

Прогоны автономны и не устанавливают брокерских соединений. Модель покрывает рублёвые контракты и маркируемую equity; доставка, ролловер, расчёты денежных потоков по расписанию клиринга и очередь исполнения не моделируются.
